Edge cases

The zero-length line, the pure vertical, and the question of who clips the screen — each resolved by one deliberate line of code.

Case 1: the line that is a point

Your test single point plots (4,4)→(4,4) and expects exactly one pixel. Trace the setup: dx = 0, dy = 0, sx = 0, sy = 0, err = 0. Then read the loop order in Points():

plot (x, y)          # first!
stop if (x, y) == B  # (4,4) == B — done, nothing ever moves
The point. Plot-then-check is what makes zero-length lines work with no special case. Had the check come first, or the moves before the plot, this test would need an if of its own. Ordering is the feature.

Case 3: who clips the screen?

Points() takes no screen argument — look at its signature. It happily returns pixels at (−2,0) or (10,10) on a 5×5 screen, because it is pure geometry. Clipping lives in exactly one place, Draw():

if p.X < 0 || p.Y < 0 || p.X >= w || p.Y >= h {
    continue  // not our pixel, not our problem
}

Your clips out of bounds points test proves it: the line (0,0)→(10,10) on a 5×5 fake screen plots exactly (0,0)…(4,4). Geometry and screen bounds never mix — that split is why Points() is trivially testable with no screen at all.
